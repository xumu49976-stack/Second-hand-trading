## 为什么先 Maven 再 MySQL

JDBC 需要 MySQL 的驱动 jar（`mysql-connector-j`）。没有 Maven，你得手动下载 jar、手动配 classpath、换台电脑再配一遍。

Maven 把这件事变成 `pom.xml` 里的一行 `<dependency>`。所以顺序是 **Maven → JDBC**，不能反。

原因：你写的是**相对路径** `out/products.txt`。相对路径是相对"**当前工作目录**"，不是项目根目录，也不是源码所在目录。

```java
File parent = file.getParentFile();
if (parent != null && !parent.exists()) { parent.mkdirs(); }
```

**问题三：命令行 `mvn` 用不了（不是你的错）**

**你问的"为什么要 src/main/java"，直接答**

这不是随便定的约定，它让 Maven 知道去哪找东西：

| 目录                   | Maven 认为里面是什么           |
| -------------------- | ----------------------- |
| `src/main/java`      | 生产代码 —— 会被打包进最终 jar     |
| `src/test/java`      | 测试代码 —— 只在跑测试时编译，不进 jar |
| `src/main/resources` | 配置文件 —— 打包时复制进 jar      |
| `target/`            | 编译产物 —— 可随时删，Maven 会重建  |

**不按这个放会怎样**：Maven 根本不去看那个目录。**不是报"路径不对"，而是默默什么都不编译**，然后你运行时报 `ClassNotFoundException`——比直接报错难查得多。

这就是"约定优于配置"：按它的规矩放，一行配置都不用写。

#### 🔍 11-10 批注

**① 依赖加了却没使用**

`pom.xml` 里确实有 commons-io，但我搜遍 `src/main/java`，`commons`、`IOUtils`、`FileUtils` **零命中**。

加了依赖不等于会用依赖——**没引用过，就等于没验证过它能不能用**。哪天坐标写错了（比如版本不存在），你也发现不了。

补一行就够，比如把 `products.txt` 整个读出来打印：

```java
String content = FileUtils.readFileToString(new File(path), StandardCharsets.UTF_8);
System.out.println(content);
```

（`FileUtils` 来自 `org.apache.commons.io.FileUtils`，这就是"依赖"的意义：不用自己写几十行读文件+关流的代码。）

**② `compile` / `test` / `package` —— 直接答**

它们是**同一条流水线上的不同停靠站**：

```
validate → compile → test → package → verify → install → deploy
```

| 命令 | 做了什么 | 产物 |
|---|---|---|
| `compile` | 只编译 `src/main/java` | `target/classes` |
| `test` | compile + 编译并**运行** `src/test/java` 里的测试 | `target/test-classes` + 测试报告 |
| `package` | test + 打包 | `target/second-hand-trading-1.0-SNAPSHOT.jar` |

**最关键的一点：后面的一定包含前面的。** 跑 `package` 会先跑 `test`，跑 `test` 会先跑 `compile`。

这解释了一个常见困惑：为什么 `mvn package` 有时会失败在"测试不通过"——因为它真的先跑了测试。你现在 `src/test/java` 是空的，所以 test 阶段等于什么都不做。
