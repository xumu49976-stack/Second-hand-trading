#### 🔍 11-16 批注

**① "保证失败能回滚"方向对了，但只说了一半**

回滚是**手段**，不是**目的**。真正的理由是**原子性**：一次业务里的多个写操作必须"全成或全败"。

拿你的项目举例，用户买一个商品要做两件事：

```sql
INSERT INTO orders (...) VALUES (...);                 -- 生成订单
UPDATE product SET stock = stock - 1 WHERE id = 1;     -- 扣库存
```

第一条成功、第二条失败（没货了），不加事务就会出现**"有订单、没扣库存"**——卖出了不存在的货。反过来先扣库存再失败，就是**"货少了、没订单"**——库存凭空蒸发。

事务保证：要么两条都成，要么都撤。

**② 现象你观察对了，但术语说反了**

你写"提交前 stock 没变，提交后变成 99，**解决了不可重复读**"。

前半句**完全正确**，这正是隔离级别在起作用。但"解决了不可重复读"这句是乱的：

- **不可重复读**是一个**问题**，不是"被解决"的对象
- MySQL 默认隔离级别是 **`REPEATABLE READ`（可重复读）**，它**防止**的就是不可重复读
- 正确说法："因为是 REPEATABLE READ 级别，**避免了**不可重复读"

四个并发问题，背这张表就够：

| 问题    | 现象                  | 默认 RR 下            |
| ----- | ------------------- | ------------------ |
| 脏读    | 读到别人**未提交**的数据      | 不会发生               |
| 不可重复读 | 同一事务内两次读**同一行**结果不同 | 不会发生（RR 就是防它）      |
| 幻读    | 同一事务内两次读**行数**变了    | 基本不会（InnoDB 间隙锁补上） |
| 丢失更新  | 两个事务互相覆盖            | 需自己加锁              |

**③ 那次 `COMMIT` 踩坑其实是成功的**

你亲眼看到"没 commit 之前别人看不到，commit 之后才看到"——这就是事务边界最直观的样子。

**❌ `try-with-resources` 你根本没写**

你的代码是普通 `try { } catch`，而且三行 `close()` 被注释掉了：

```java
try {
    Connection con = DriverManager.getConnection(...);
    ...
}catch (SQLException e){
    e.printStackTrace();
}
//        //7、释放资源
//        resultSet.close();
```

**你批注里写"try catch 会自动添加 finally 来调用 close 关闭"——这句话是错的：**

| 写法                          | 会自动 close 吗                           |
| --------------------------- | ------------------------------------- |
| `try { } catch { }`         | **不会**。catch 只处理异常，跟关闭资源无关            |
| `try { } finally { }`       | 不会自动 close，得你自己在 finally 里写 `close()` |
| **`try (Res r = ...) { }`** | **会**。这才是 try-with-resources          |

**区别就在那对小括号。有圆括号才叫 try-with-resources。**

正确写法：

```java
try (Connection con = DriverManager.getConnection(url, user, pwd);
     Statement stmt = con.createStatement();
     ResultSet rs = stmt.executeQuery(sql)) {

    while (rs.next()) { ... }

} catch (SQLException e) {
    e.printStackTrace();
}
```

三个资源一起放进圆括号，**离开 try 时按"后开先关"自动关闭**——正是你描述的那个顺序，只是交给编译器执行。

**这个错为什么现在没炸**：JVM 退出时操作系统回收 socket，连接自然断了，demo 里看不出泄漏。

**❌ 但防注入的原理你答错了**

你写"拼接 SQL 语句会把 `'` 转译为 `\'` 避免了注入"。**不是转义。** 如果真靠转义，"宽字节注入"（用 `%bf%27` 这类编码绕过）还能打穿。

真正的机制是**参数与 SQL 结构彻底分离**：

|          | 字符串拼接                           | `PreparedStatement` |
| -------- | ------------------------------- | ------------------- |
| SQL 何时形成 | 运行时拼好**整句**，一次送给数据库解析           | `?` 模板**先**编译，结构已固定 |
| 参数是什么    | 变成 SQL **语法的一部分**，能改变结构         | 只当**数据**，走独立通道传输    |
| 注入结果     | `' OR '1'='1` 改掉了 WHERE 结构 → 全表 | 被当成一个普通字符串值 → 查不到   |

一句话：**拼接是"把用户输入编进语法"，参数化是"语法先定死、输入只当值"。** 不是把危险字符转义掉，是压根不让它进入语法解析。

**❌ 一个真 bug：删除失败也报"成功"**

```java
int c = deleteptmt.executeUpdate();

} else {
    System.out.println("删除成功！！");    // ← 失败也报成功
}
```

这是最危险那类 bug——**失败了报成功**。和你 10-26 那个 `setName` 一个性质：什么都没做，却告诉调用方成了。

**❌ 硬编码主键，脚本只能跑一次**

正确写法交给自增：

```java

```
