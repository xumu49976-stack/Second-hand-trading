### ① 外键报错：你贴的不是外键错误

你贴的是：

```
SQL 错误 [1064] [42000]: You have an error in your SQL syntax
... near 'where id = 1' at line 1
```

**1064 是"语法错误"**——SQL 语句本身写坏了，数据库还没轮到检查外键就把它拒了。

我替你跑了一遍真正的删除：

```
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails
(`second_hand`.`product`, CONSTRAINT `fk_product_category`
 FOREIGN KEY (`category_id`) REFERENCES `category` (`id`))
```

**两个错误码的意义完全不同：**

| 错误码 | 含义 | 说明 |
|---|---|---|
| 1064 | 语法错误 | 句子写坏了，数据库读不懂 |
| **1451** | 外键约束失败 | 句子读懂了，但**规则不许你这么干** |

1064 是你打错了字；1451 是**数据库在保护数据**。排查时这是两回事。

另外任务写的是 `id = 2`（食品，挂着 2 个商品），你写的是 `id = 1`。编号错了不影响结论（数码也挂着 1 个商品，同样会报 1451），但说明你可能是手打没照抄。

**这件事的意义**：你到现在**还是没见过外键拦人的样子**。所以昨天 `CASCADE` 记反、今天又贴错报错——同一个根子，没真正动手验证。

#### 🔍 11-16 批注

**① "保证失败能回滚"方向对了，但只说了一半**

回滚是**手段**，不是**目的**。真正的理由是**原子性**：一次业务里的多个写操作必须"全成或全败"。

拿你的项目举例，用户买一个商品要做两件事：

```sql
INSERT INTO orders (...) VALUES (...);                 -- 生成订单
UPDATE product SET stock = stock - 1 WHERE id = 1;     -- 扣库存
```

第一条成功、第二条失败（没货了），不加事务就会出现**"有订单、没扣库存"**——卖出了不存在的货。反过来先扣库存再失败，就是**"货少了、没订单"**——库存凭空蒸发。

事务保证：要么两条都成，要么都撤。

**② 现象你观察对了，但术语说反了**

你写"提交前 stock 没变，提交后变成 99，**解决了不可重复读**"。

前半句**完全正确**，这正是隔离级别在起作用。但"解决了不可重复读"这句是乱的：

- **不可重复读**是一个**问题**，不是"被解决"的对象
- MySQL 默认隔离级别是 **`REPEATABLE READ`（可重复读）**，它**防止**的就是不可重复读
- 正确说法："因为是 REPEATABLE READ 级别，**避免了**不可重复读"

四个并发问题，背这张表就够：

| 问题 | 现象 | 默认 RR 下 |
|---|---|---|
| 脏读 | 读到别人**未提交**的数据 | 不会发生 |
| 不可重复读 | 同一事务内两次读**同一行**结果不同 | 不会发生（RR 就是防它） |
| 幻读 | 同一事务内两次读**行数**变了 | 基本不会（InnoDB 间隙锁补上） |
| 丢失更新 | 两个事务互相覆盖 | 需自己加锁 |

**③ 那次 `COMMIT` 踩坑其实是成功的**

你亲眼看到"没 commit 之前别人看不到，commit 之后才看到"——这就是事务边界最直观的样子。
