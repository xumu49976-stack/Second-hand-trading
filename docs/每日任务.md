**二、决策 B 的理由写得对**

> "实体类的身份（Identity）应该由其唯一主键（ID）决定，而不是由它的可变业务属性（如价格）决定。"

这就是 JPA / Hibernate 的标准做法（`@Id` 参与的 `equals`），不是你自己拍脑袋拍的。而且你顺手把最容易漏的那半个问题答对了——**两个都没入库的对象（id=0）互相 `equals` 该是 false**。实测：

```
两个都没入库(id=0)：u1.equals(u2) = false，HashSet.size = 2   ← 符合你的设计
入库的 a 与未入库的同内容对象：equals = false
两个都是库里 id=1 的对象：equals = true，hashCode 相同，HashSet.size = 1   ← 期望 1
```

很多人这里直接写 `return id == p.id;` 就收工，结果两个新对象 id 都是 0 → 被判为相等 → 往 `HashSet` 里塞两个只留一个，另一个被悄悄吞掉。你返回 `false` 兜住了，这个处理是对的。

**三、但 B 方案有一笔副作用，记着就行：hashCode 是可变的**

`hashCode` 用 id，而 id 会在入库时被回填（0 → 正数）。也就是说**对象放进 `HashSet` 之后，它的 hashCode 变了**。实测：

```
Set<Product> s3 = new HashSet<>();
s3.add(p);                 // 此时 p.id = 0
p.setId(999);              // 模拟 insert 回填
hashCode 1107730949 -> 999（变了）
s3.contains(p) = false     ← 自己放进去的，找不回来了
```

现在不影响你，因为你没有把"未入库对象"放进集合。但往后只要出现"先塞进 `HashSet`/`Map` 再入库"，就会丢对象。三条路，选一条写进注释（不给代码）：

1. **约定**：对象入库后才可以当集合的 key（最省事，靠自律）
2. **`id` 设 `final`**，入库不靠回填而是返回新对象（最干净，但要改构造方式）
3. 集合改用 identity 语义（等于放弃"按 id 去重"）

**四、你的踩坑现象，信息量比看起来大**

```
java.sql.SQLException: Generated keys not requested. You need to specify
  Statement.RETURN_GENERATED_KEYS ...
```

注意：**异常抛出时，INSERT 已经成功了**。`executeUpdate()` 那行已经执行、行已经写进库，失败的是"取 id"这一步。于是：

- 库里多了一条"鸡腿"

**一次"部分成功"比一次"彻底失败"更危险**——数据写进去了，程序却以为没有。这正是 11-16 那节事务要解决的问题：如果"插入商品"和后续操作属于同一个业务单元，它们应该在同一事务里，要么全成、要么全回滚。现在你的 DAO 每个方法各开各的连接，跨方法的事务没地方挂——这是 V0.3 之后要面对的结构问题，先记着，不用现在改。

**五、`select max(id)` 那题：观察对，结论错**

你写"我感觉这样可行"，然后解释了跳号（id=5 之后下一个给 10，因为中间 6–9 被消耗了）。**跳号这个观察是对的**，说明你真的看了数据。但它不是 `max(id)` 不能用的原因。

致命伤是**并发**：

```
连接A: insert 鸡腿      -> 数据库分配 id=11
连接B: insert 可乐      -> 数据库分配 id=12
连接A: select max(id)   -> 拿到 12        ← 这是 B 的商品！
连接A: update ... where id=12             ← 把 B 的可乐改了
```

两个用户同时发布，就会改错别人的数据。跳号只是"你一个人跑"时的现象，并发是"多连接同时跑"时的事故。另外两个次级理由：`max(id)` 多一次往返查询，而 `getGeneratedKeys()` 随 insert 一起返回、零额外成本；哪天换成 UUID 主键或分库分表，`max(id)` 直接失效。

> **一句话记住**：`getGeneratedKeys()` 拿的是"**这条语句插入的那一行**"的 id，由数据库在插入的同一刻给出；`max(id)` 是"猜一个当前最大的数"，猜的是**全表**，不是你那行。
