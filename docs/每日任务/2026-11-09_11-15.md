## 为什么先 Maven 再 MySQL

JDBC 需要 MySQL 的驱动 jar（`mysql-connector-j`）。没有 Maven，你得手动下载 jar、手动配 classpath、换台电脑再配一遍。

Maven 把这件事变成 `pom.xml` 里的一行 `<dependency>`。所以顺序是 **Maven → JDBC**，不能反。

| -------------------- | ----------------------- |

**② `compile` / `test` / `package` —— 直接答**

它们是**同一条流水线上的不同停靠站**：

```
validate → compile → test → package → verify → install → deploy
```

| 命令        | 做了什么                                     | 产物                                            |
| --------- | ---------------------------------------- | --------------------------------------------- |
| `compile` | 只编译 `src/main/java`                      | `target/classes`                              |
| `test`    | compile + 编译并**运行** `src/test/java` 里的测试 | `target/test-classes` + 测试报告                  |
| `package` | test + 打包                                | `target/second-hand-trading-1.0-SNAPSHOT.jar` |

**最关键的一点：后面的一定包含前面的。** 跑 `package` 会先跑 `test`，跑 `test` 会先跑 `compile`。

这解释了一个常见困惑：为什么 `mvn package` 有时会失败在"测试不通过"——因为它真的先跑了测试。你现在 `src/test/java` 是空的，所以 test 阶段等于什么都不做。

**② 你答"用 DECIMAL，不知道为什么"——现在补上**

`DECIMAL` 和 `DOUBLE` 的根本区别是**怎么存小数**：

- **`DOUBLE`**：二进制浮点。0.1 在二进制里是**无限循环小数**，只能存近似值
- **`DECIMAL`**：定点数，按十进制存，**精确**

经典后果：

```sql
SELECT 0.1 + 0.2 = 0.3;                    -- 0（假）
SELECT CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE);   -- 0.30000000000000004
```

Java 里一样：`0.1 + 0.2 == 0.3` 是 `false`。

金额**一分钱都不能差**。累加一万笔 0.1 元，`DOUBLE` 会差出几分；`DECIMAL` 一分不差。

**代价**：DECIMAL 运算比 DOUBLE 慢（用软件模拟十进制运算）。但金额运算量小，可以忽略。

**什么时候 DOUBLE 能放心用**：科学计算、图形、统计——只要"近似值可接受"。

**③ 你项目里的债**

`Product.price` 现在是 `double`，和数据库的 `DECIMAL` 对不上。学到 JDBC 那步会用到 `BigDecimal`，那时一起改。**现在别动**。

| 题         | 你的 SQL                 | 实际结果           | 判定  |
| --------- | ---------------------- | -------------- | --- |

| 数量 + 均价   | `count(*), avg(price)` | 3 / 79.166667  | ✅   |

**① `group by stock > 10` 这个写法很聪明**

大部分人只会 `group by` 一个列，你直接分组一个**布尔表达式**。MySQL 完全支持，结果也正确。这个技巧在做"区间统计"时很实用。

**② `avg(price)` 返回了 79.166667——这里有个坑**

`price` 是 `DECIMAL(10,2)`，但 `avg` 的结果是**六位小数**。平均值运算会提升精度。

金额场景下这很关键：**数据库算出来的平均值不能直接拿去显示或再参与金额计算**。要么 `ROUND(avg(price), 2)`，要么在 Java 侧用 `BigDecimal` 格式化。

这是"用 DECIMAL 也不等于自动帮你处理精度"的典型例子。

**③ `WHERE` vs `HAVING` 你答对了**，补使用场景：

- `WHERE` 筛**行**，不能用聚合函数（`where count(*) > 2` 会报错）
- `HAVING` 筛**组**，必须配合 `GROUP BY`，可以用聚合函数
- 能放 `WHERE` 的条件别放 `HAVING`——先筛行再分组，数据量小得多

**② 但 `CASCADE` 和 `RESTRICT` 你答反了，而且错得很危险**

你写"这俩是一样的作用，属于默认行为……有则拒绝删除"。**它们不是一样的，作用正好相反**：

| 选项 | 行为 | 记忆 |
|---|---|---|
| `RESTRICT` / `NO ACTION` | **拒绝**删除父记录，报错 | "拦住你" |
| `CASCADE` | **级联删除**——父记录删了，子记录跟着一起删 | "跟着走" |
| `SET NULL` | 把子表外键置为 `NULL` | "断开关联" |

用你的场景演示：

```sql
-- 你的外键是默认的 RESTRICT
DELETE FROM category WHERE id = 2;   -- 报错：食品下还有 2 个商品

-- 如果改成 ON DELETE CASCADE
DELETE FROM category WHERE id = 2;   -- 成功，康师傅和米雪被一起删掉
```

**为什么危险**：`CASCADE` 会**静默删掉一大片数据**。删一个分类，下面几十个商品全没了，数据库一声不响。生产环境几乎都用 `RESTRICT`，就是要"拦住你别乱删"。

**这也解释了那条"删分类"任务为什么重要**——真做过的话，你会看到 `Cannot delete or update a parent row: a foreign key constraint fails`，也就不会把两者搞混。

**③ 三个地方没交实物**

- **外键报错没贴**（任务明确要求"原样贴给我"）
- **自出的 3 条查询没贴**
- **复盘四问没写**

前两个可以算忘了记录；第三个不行——复盘四问是这周唯一的自我检查，跳过等于这周没总结。

**④ 力扣 136 正确**

用 `Map` 计数，`getOrDefault(num, 0) + 1` 用得干净，O(n)。

补充：这题更漂亮的解法是**异或**——`a ^ a = 0`、`a ^ 0 = a`，全部元素异或一遍，成对的消掉，剩下的就是答案。O(1) 空间。但你的 Map 解法更通用（如果"其他元素出现 3 次"就不行了，那时候要用位运算计数），所以先写对再说。
