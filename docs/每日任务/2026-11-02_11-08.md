## 先补三个概念（看完截进你的笔记本）

### ① `remove(int)` 和 `remove(Object)` —— 不是"错 1 个单位"

你写的是"本质是实际位置和下标错了 1 个单位，容易删错"。**这个理解不对，需要纠正。**

两个方法不是"同一件事的两种写法"，而是**两种完全不同的操作**：

| 写法                  | 语义                           | 传 `3` 的结果                         |
| ------------------- | ---------------------------- | --------------------------------- |
| `remove(int index)` | 删掉**第 index 个位置**的元素，跟元素内容无关 | 删掉下标为 3 的那个（第 4 个）                |
| `remove(Object o)`  | 找一个**内容等于 o** 的元素删掉，跟位置无关    | 删掉内容等于数字 3 的元素（假设列表存的是 `Integer`） |

不存在"差 1"，因为一个讲**位置**、一个讲**内容**，量的根本不是同一个东西。

容易踩坑的地方在这里：`ArrayList<Integer>` 里存了 `[10, 20, 30]`，你写 `list.remove(1)` —— 删掉的是 `20`（下标 1），不是值为 1 的元素。想删"值为 1 的元素"必须写 `list.remove(Integer.valueOf(1))`。

而 `ArrayList<Product>` 不可能有这个问题，因为 `Product` 不是 `int`，`remove(product)` 一定走 `remove(Object)`。你上周真正遇到的风险是另一个：**`remove(Object)` 内部用 `equals` 比较，而你的 `Product` 当时还没重写 `equals`** —— 现在重写过了，这条路已经通了。

### ② `boolean` 还是异常 —— 什么时候用哪个

你的原话是"感觉没必要用 boolean 了，目前还不知道什么场景适用哪个"。给你一条能直接用的判断标准：

|     | 返回 `boolean`                           | 抛异常                           |
| --- | -------------------------------------- | ----------------------------- |
| 适合  | **失败是预期内、常见、需要调用方继续处理**的情况             | **失败不该发生、或发生了就没法继续**的情况       |
| 例子  | 用户填的价格不合法（要提示重填，流程继续）                  | 程序内部状态崩了、参数是 bug（继续跑只会更糟）     |
| 调用方 | `if (setPrice(x)) { ... } else { 提示 }` | `try { ... } catch { 记录并中止 }` |
| 代价  | 轻，不需要栈信息                               | 重，要创建异常对象、要捕获                 |

**口诀：这个失败，调用方是"能接着干"还是"干不下去了"？**

- 能接着干（让用户重填、换一个商品再试）→ 返回 `boolean` 或状态码
- 干不下去（数据已经坏了、参数根本不该传进来）→ 抛异常

放到你的项目里：

- `setPrice` 服务的是"用户改价"这个交互 → **`boolean` 更合适**，价格填错是常态，要提示重填
- `Product` 构造方法服务的是"我要造一个商品" → **抛异常更合适**，拿着负数去造商品，说明调用方代码写错了
- 所以**两个都保留是对的**，不是"有一个多余"

同一个类里两种风格并存不是矛盾，是**按"失败该由谁负责"分工**。

### ③ `printStackTrace()` 什么时候能用

你笔记里已经写了正确的一半："打印信息不停止"。那为什么不能当"友好提示"用？

三个原因：

1. **它不是说给用户听的。** `at com.campus.trade.Product.setPriceOrThrow(Product.java:54)` 这种输出，用户看不懂，只有开发者能看。
2. **它只"印"，不"断"。** 打印完程序继续跑，后面的代码拿着坏数据往下走。
3. **它把异常从"信号"降级成"噪音"。** 异常本来能让调用方决定怎么办，你印完就算了，等于放弃了控制权。

**什么时候可以用？**

- **调试时**：想快速看异常从哪冒出来，临时加一句，调完删掉
- **程序最顶层兜底**：`main` 或全局异常处理器里，确认异常已无法挽回，打印完整堆栈给人排查用。这是它唯一"正当"的生产用途

**你的 `Main` 里那两处该改成：**

```java
try {
    Product p = new Product("坏商品", -5, 1);
} catch (IllegalArgumentException e) {
    System.out.println("创建失败：" + e.getMessage());   // 只给人看一句话
}
```

`e.getMessage()` 拿到的就是你 `throw` 时写的 `"价格不能为负：-5.0"` —— 因为消息里带了具体数值，这句话本身就是完整的提示。

#### 🔍 11-03 验收批注

**① `InvalidPriceException` 建对了，但 `Main` 里有个 catch 没跟上 —— 程序崩了**

实际运行结果：

```
Exception in thread "main" com.campus.trade.InvalidPriceException: 价格不能为负：-1.0
    at com.campus.trade.Product.setPriceOrThrow(Product.java:54)
    at com.campus.trade.Main.main(Main.java:49)
```

原因：`InvalidPriceException extends RuntimeException`，**它和 `IllegalArgumentException` 没有父子关系**。而 `Main` 第 50 行写的是 `catch (IllegalArgumentException e)`，类型对不上，接不住，异常一路冒出 `main`，程序终止。

**注意：编译器不会提醒你。** 异常是运行时按类型匹配的；非受检异常编译器压根不管你 catch 得对不对。这种 bug 只能靠跑出来。

两种改法，明天二选一：

- **A**：把第 50 行改成 `catch (InvalidPriceException e)`
- **B**：把 `InvalidPriceException` 改成 `extends IllegalArgumentException`

**推荐 B**，理由见下条。

**② 你答"见名知意"，对了一半**

你写的是"自定义异常可以做到见名知意，主要为了那个异常类的名字"。这是**最直观的理由，但不是全部**。还有两个更实际的作用：

1. **分类捕获**：调用方可以只 `catch (InvalidPriceException e)` 处理价格问题，让别的 `RuntimeException` 继续往上抛。若全用 `IllegalArgumentException`，你就分不清"价格非法"和"库存非法"——想分开处理只能比 `getMessage()` 字符串，极不靠谱。
2. **携带业务数据**：

```java
public class InvalidPriceException extends IllegalArgumentException {
    private final double offendingPrice;
    public InvalidPriceException(double offendingPrice) {
        super("价格不能为负：" + offendingPrice);
        this.offendingPrice = offendingPrice;
    }
    public double getOffendingPrice() { return offendingPrice; }
}
```

catch 方直接 `e.getOffendingPrice()` 就能拿到越界的值去记日志、去回显，不用从消息里抠数字。

**关于继承谁**：`extends RuntimeException` 还是 `extends IllegalArgumentException`，决定了**谁能接住它**。想让老代码的 catch 继续生效，就继承对应的标准异常——这是很实用的一条经验。

## 附：递归速成（你卡住的地方）

你说"主要是递归没想到也不熟练"。判断是对的：这题卡的不是 File API，是**怎么在层级里往下钻**。

### 一、递归只有三件事

1. **出口**：什么时候停下来，不再往下
2. **缩小**：把大问题变成一个同类的小问题
3. **信任**：假设"小问题已经解决了"，你只管拿它的结果

第 3 条是新手最难接受的——**递归不需要你在脑子里展开所有层级**。你只要相信"我这个方法对更小的输入是对的"，然后把它当黑盒用。

### 二、先拿你会的问题热身

"求 1 到 n 的和"，你会用循环：

```java
int sum = 0;
for (int i = 1; i <= n; i++) sum += i;
```

递归版没有循环：

```java
int sum(int n) {
    if (n == 1) return 1;        // 出口
    return n + sum(n - 1);       // 缩小 + 信任
}
```

`n == 1` 是出口，`n + sum(n-1)` 是"n 的和 = n 加上 n-1 的和"。**循环被藏进了"自己调自己"里。**

### 三、套到你的目录上

把"一个目录"看成一个节点，它只有两种身份：

| 身份         | 怎么办                    |
| ---------- | ---------------------- |
| **文件**（叶子） | 不再往下钻，判断后缀，返回 0 或 1    |
| **目录**（分支） | 对每个孩子调用**同一个方法**，结果加起来 |

对着上面三件事填：

- **出口**：`file.isFile()` 为 true 时，不再递归
- **缩小**：孩子比父亲"小"——孩子要么是没有下级的文件，要么是更浅的目录
- **信任**：`sum += countJava(child)` 这一行，你不需要知道 child 里面有多深，相信它会自己数完

### 四、骨架（空两处，你填）

```java
public int countJava(File file) {
    // 出口：是文件就不再往下
    if (file.isFile()) {
        return 1;                       // 名字以 .java 结尾 → 1，否则 → 0
    }

    // 分支：是目录，让孩子自己去数
    int sum = 0;
    File[] children = file.listFiles();
    for (File child : children) {
        sum += countJava(child);                       // 对每个孩子调用同一个方法
    }
    return sum;
}
```

### 五、三个坑，提前说

1. **`listFiles()` 可能返回 `null`**（目录不存在、或没有读权限）。直接 `for` 会抛 NPE。
2. **后缀大小写**：`.JAVA` 算不算？先想清楚再写。
3. **传进去的必须是目录**：如果传了个文件进去，会走出口那支——这其实正好体现递归的优雅。

#### 答疑：为什么"用名称做 key"是错的

**① Map 的硬规则：key 唯一，重复就覆盖**

```java
Map<String, Product> map = new HashMap<>();
map.put("高数教材", book1);
map.put("高数教材", book2);
System.out.println(map.size());   // 1  ← book1 没了
```

`put` 重复 key **不报错、不提示**，直接覆盖。比抛异常更危险——数据在**无声无息中丢失**。

这就是"名称不能做 key"的根本原因。你昨天说"同名商品可以存在"和今天这句反驳，是同一个判断，都对。

**② 那要不要把 List 换成 Map？**

不一定，取决于你想优化什么。两种正确形态：

**方案 A：加 `id`，用 id 做 key（Map 替代 List）**

```java
private Map<Long, Product> products = new LinkedHashMap<>();
```

`Product` 加 `long id`，key 天然唯一。代价是要维护 id 生成。这就是你说的"ISBN / 身份证号"，V0.3 会做。

**方案 B：List 当主存储，Map 当索引（两者并存）**

```java
private List<Product> products = new ArrayList<>();                 // 主数据
private Map<String, List<Product>> indexByName = new HashMap<>();   // 名称 → 同名列表
```

名称做 key，但 value 是 **List**（一对多），不丢数据。`searchByName` 从 O(n) 变 O(1)。代价是增删要同时维护两个结构。

**③ 真实项目为什么两个都留**

| 需求        | 谁合适                     |
| --------- | ----------------------- |
| 展示全部商品、保序 | `List`                  |
| 按 id 精确查  | `Map<id, Product>`      |
| 按名称搜      | `List` 遍历，或 `Map` 做倒排索引 |
| 分页        | `List`                  |

**List 管"顺序和全部"，Map 管"快速定位"——互补，不是替代。**

**④ `Main` 里 `loadFromFile` 不见了**

现在只剩末尾的 `saveToFile`。没有 load，"关掉再打开数据还在"这件事仍然没被验证。这是 V0.2 的核心目标，别漏。

**⑤ `indexByName` 放哪：另开类还是放 `ProductManager` 里？**

**答：放 `ProductManager` 里，作为一个私有字段。** 不是方法，也不是新类。

```java
public class ProductManager {
    private List<Product> products = new ArrayList<>();                 // 主数据
    private Map<String, List<Product>> indexByName = new HashMap<>();   // 索引：名称 → 同名列表

    public List<Product> searchByName(String name) { ... }              // 对外只暴露这一个
}
```

三条理由：

1. **它是"状态"不是"行为"。** 方法装动作，字段装数据。`indexByName` 是数据，所以是字段。写成方法毫无意义——方法不能持有状态。

2. **对外是私有字段。** 调用方只该调 `searchByName("高数教材")`，根本不知道你内部有张索引表。索引是实现细节，暴露出去等于把内部结构焊死，以后改不动。

3. **最关键：它必须和 `products` 永远保持一致。** 这两个结构是"一份数据、两种组织方式"。只要拆到两个类，就变成"谁负责同步？"——跨类同步是 bug 的温床，一边加了一边忘了减，数据就悄悄错位。**放在一个类里，一个类负责一致性，这是封装的意义。**

**什么时候才该另开一个类？**

判断标准：**索引逻辑复杂到一定程度才拆。** 比如以后你要同时维护

- 按名称的索引
- 按价格区间的索引
- 按分类的索引
- 按发布时间的索引

这时可以抽出一个 `ProductIndex` 类，专门管所有索引，由 `ProductManager` 持有：

```java
public class ProductManager {
    private List<Product> products = new ArrayList<>();
    private ProductIndex index = new ProductIndex();   // ← 索引多了才抽出去
}
```

但现在你只有**一个**索引，抽类就是过早抽象，纯增加理解成本。

> 一句话：**先问"它和主数据是否必须始终一致"，是 → 放同一个类。**

**同步的四个地方（这是唯一的难点，别漏）**

| 操作             | `products`        | `indexByName`                        |
| -------------- | ----------------- | ------------------------------------ |
| `addProduct`   | `add(p)`          | 把 p 加进 `indexByName.get(名称)` 那个 List |
| `removeByName` | `remove(p)`       | 从对应 List 移除；**List 空了要把整个 key 也删掉**  |
| `loadFromFile` | `clear()` 后重新 add | **也要 `clear()`**，否则旧索引残留             |
| `saveToFile`   | 不涉及               | 不涉及                                  |

那个"List 空了删 key"很容易忘，后果是：`searchByName` 返回一个空 List（应该返回"没有"），而且 Map 里堆一堆没用的空 key。

**建议的力扣题：217. 存在重复元素**

这题会逼你认识新结构 **`Set`**：

- `Set` 是"不许重复的集合"，`add` 时元素已存在会返回 `false`
- 解法：遍历数组，`if (!set.add(x)) return true;`
- 对比：`List` + `contains` 是 O(n²)，`Set` 是 O(n)

正好接上刚学的 `Map`——`Map` 是键值对，`Set` 是只有键没有值，底层都是哈希表。
